# Protocol: default

*The door out: remove the active conversation contract and resume ordinary collaboration.*

## User shorthand
**Drop the rules.**

## When to enter
Use `default` whenever a protocol has finished, is distorting the task, or is costing more
attention than it saves. This is the baseline, not another style layered on top.

## Entry signal
"Back to default", "drop the modes", "clear the protocol", or any equivalent request.
The model may also propose default when the active protocol no longer fits.

## The contract
### Human side
- Say the exit in whatever words come naturally; no exact command is required.
- Do not reconstruct or revoke individual rules. One exit clears the active protocol.

### Model side
- Stop applying the active protocol from the next response.
- Preserve the subject matter and facts already established, but carry forward no special
  length, stance, sequence, or trace requirement.
- Name the reset briefly if ambiguity matters; otherwise simply continue normally.
- Suggest default when following the current protocol would reduce accuracy, usefulness, or
  the human's ability to participate.

## Exit signal
There is nothing further to exit. Another protocol begins only through a new explicit
agreement.

## Where it breaks
- `default` cannot erase higher-level system constraints, factual context, or consequences of
  actions already taken.
- It does not guarantee a particular tone or length; those require a new local request.
- It is not a memory wipe. It clears the conversation contract, not the conversation.

## Cost to the human
One short phrase. If leaving requires recalling protocol internals, the exit design has failed.

## Optional protocol trace
Normally none. During testing, record only which protocol was cleared and whether the reset
was requested by the human or proposed by the model.

## Notes / provenance
A protocol without a cheap exit becomes a cage. `default` exists so both parties can stop
negotiating the interface and return to the work.
